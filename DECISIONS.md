# Decisions

Impact `foundation`: other slices build on it, expensive to change. Impact `easy-to-change`: a value or look that can be retuned in minutes. Status is `open` until Manuel has seen it at review, then `accepted` or `changed`.

| D-016 | 1.1 | All card sizes (text, padding, counter, decor shapes and their offsets) are written in "ref px" measured on the 280x520 mockup card and scaled with the card width via a CSS container query unit (`--u` = `100cqw / --ref-width`). | D-021 | 1.2 | `QuestionGroup` lives in `src/content/types.ts` (exactly the SPEC 3.1 shape); `src/deck/` imports it from there, slice 1.3 re-exports it from `src/content/de.ts` | define it in `src/deck/types.ts`; wait for `de.ts` | keeps deck independent of the German data module and avoids a circular dependency between content and deck | easy-to-change | open |
| D-022 | 1.2 | Deck order: draw a random remaining card each step (weighted by group size), but only from groups that still leave an arrangement without adjacent same-group cards (largest remaining group at most ceil(m/2), at most floor(m/2) if it is the group just played). This finds a valid order exactly when one exists (largest group at most ceil(n/2)). If none exists, the fallback draws from the biggest other group | shuffle then repair adjacent pairs; fixed interleave pattern; retry random shuffles | repair and retry only work "usually"; the forced choice is exact and keeps the shuffle random | foundation | open |
| D-023 | 1.2 | State machine: `GameState` is a union on `phase` (`start`, `card` with `deck`, `index`, `total`, `end` with `deck`); `advance(state, groups, rng = Math.random)` is pure. A deck with no cards goes straight from start (or end) to the end card | `total` derived from `deck.length`; separate "empty" phase | the UI reads `index + 1` / `total` for the counter without extra helpers; an empty deck can only happen with broken content, so no extra phase | easy-to-change | open |
| D-024 | 1.3 | Content v1 has 34 groups (24 pairs, 5 trios, 5 singles, 68 cards; after the Phase 1 review 33 groups, 23 pairs, 5 trios, 5 singles, 66 cards, see D-031), all questions at most 45 characters. Groups were picked by asking "is there one short answer that fits every question, and does the sibling question give a funny wrong guess?" ("Montag" fits best and worst weekday, "Spinnen" fits fear now and as a child, "Bruno" fits first pet and favourite cuddly toy). Each theme (food, sweets, drinks, animals, music, films, books, travel, hobbies, jobs, school, weekdays and time, weather and seasons, colours, smells, phone, skills, habits, small annoyances, small fears, places, names, numbers, words) has at most 3 groups. Trios: age / felt age / shoe size; siblings / countries / sleep hours; birthplace / home / dream home; wake-up / lunch / bedtime; words (overused / beautiful / always misspelled). Singles are open questions whose answer does not give the question away | more singles; sharper or more personal questions | the game needs same-answer overlap above all; light, easy openers suit strangers | easy-to-change | open |
| D-025 | 1.3 | Tone: informal "du", short plain questions, no double questions, no jokes at someone's expense. No partner, family-conflict, money, body, politics or religion questions at all (not only the keyword list). Job question "Was machst du beruflich?" was kept as standard small talk and paired with "Was wolltest du als Kind werden?" (the answer "Lehrerin" fits both); removed after the review, see D-031 | leave jobs out | common opener; the pair gives a good wrong guess | easy-to-change | open |
| D-026 | 1.3 | The excluded-topic test matches whole words with Unicode lookarounds (`\b` does not handle umlauts) and case-insensitively, and its list is wider than SPEC 3.1 (adds inflections and partner/marriage/diet/earning words). The matcher itself is unit-tested ("Auswahl", "Kilometer" do not hit). Keyword scanning is a safety net, not a replacement for review | exact SPEC list only; substring match | whole words avoid false alarms; a wider list catches near misses | easy-to-change | open |
| D-027 | 1.4 | Card change: the new card is mounted on top of the old one in the same grid cell (`.stage` is a one-cell grid), both play a CSS keyframe animation (`card-slide-in` from `translateX(100% + margin)`, `card-slide-out` to `translateX(-20%) scale(.95)`), all values from `transition` in theme.ts via `--transition-*` variables. The old card is removed on the new card's `animationend`; a timer at duration + 120ms (`fallbackSlackMs`) releases the lock if no event comes (hidden tab, throttled frames), so the lock cannot get stuck | Web Animations API; CSS transition classes; fixed timer only | keyframes keep the look in CSS and theme.ts; event plus timer covers both normal and throttled pages. Verified by reading the computed animation timing (380ms, the easing, keyframes), not by wall-clock, because the browser pane renders at about 1 frame per second when unfocused | easy-to-change | open |
| D-028 | 1.4 | Input: one `click` listener on `document` (a tap anywhere, also outside the card) and one `keydown` listener (Enter, Space, ArrowRight; key repeat and Ctrl/Meta/Alt combos ignored). Both go through one `advanceGame` that ignores input while `busy`. Reduced motion is read with `matchMedia` at each transition: the slide becomes a 150ms linear crossfade (`reducedFadeMs`) | `pointerdown`; CSS-only media query | `click` does not fire on scroll or drag gestures; reading it per transition respects a changed OS setting without a reload; JS needs to know the duration for the timer anyway | easy-to-change | open |
| D-029 | 1.4 | Pure parts live in `src/ui/flow.ts` and are unit-tested without a DOM (state to card spec, busy lock, key filter, screen reader text); DOM parts are `transition.ts`, `game.ts`, `main.ts`. A visually hidden `aria-live="polite"` region announces "Frage n von N: ..." and the end text on each change (the start card is not announced; it is already in the page). Nothing is made focusable | `aria-label` on the stage; jsdom tests | smallest thing that gets the new question to a screen reader; no new dependency | easy-to-change | open |
| D-030 | 1.5 | Card text weight is 500 (was 700), one constant `font.weight` in `theme.ts` for question, counter, start label, hint and the large titles; no second constant. Compared 400, 500 and 600 at 390x844 on the red, yellow and teal cards with a short and a long question. 400 is the easiest to read in size but the strokes get thin and lose the friendly look, especially white on teal and red; 600 is still clearly heavy; 500 reads cleanly and keeps the rounded Fredoka character. Small text (counter, label, hint) reads fine at 500, so it does not get a heavier weight. The start and end titles are `h1` and the browser default (bold) overrode the constant, so `.card__title` now has `font-weight: inherit`. The longest question at 360x640 needs no `--fit` shrink | 400; 600; a heavier weight for small text | the review said the bold text was hard to read; 500 is the smallest change that is clearly lighter and still friendly | easy-to-change | open |
